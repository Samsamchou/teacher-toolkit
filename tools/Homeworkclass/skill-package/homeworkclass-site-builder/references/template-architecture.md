# Sanitized Homeworkclass template architecture

Read this before copying or changing `assets/homeworkclass-template/`.

## What the template is

The bundled template is an unbound, synthetic Homeworkclass application for one active semester. It preserves the verified product baseline—weekly schedule, homework, submissions and late returns, classroom incidents, reports/exports, timetable exceptions, national holidays, six-digit teacher PIN backend, App Check, and responsive layout—while replacing teacher-specific semester data with generated configuration.

The template proves initial clone generation. It is not evidence that an existing legacy production site has already been migrated to multi-semester storage.

## Generated input boundary

`bootstrap_clone.py` replaces `src/data/semester.json` with confirmed normalized data and generates `firestore.rules` from `firestore.rules.template`.

Normalized shape:

```text
contractVersion
semester: id, label, siteTitle, startDate, endDate, timezone, sourceNote
subjects[]: id, label, shortLabel, displayOrder
classes[]: id, label, shortLabel, displayOrder, accent, accentSoft, ink, seats[]
periods[]: id, label, displayOrder, startTime, endTime
schedule[]: id, weekday, periodId, classId, subjectId, note?
```

Class, subject, and period IDs are strings validated at import. UI order comes from `displayOrder`; a period ID such as `p0` is not inferred from its label. Weekday values support 1–7.

The following product enums remain fixed because they define app behavior rather than a teacher's timetable:

- homework types;
- submission outcomes and missing reasons;
- classroom incident categories;
- timetable exception types.

## Data and write boundary

All assignments, submission events, classroom incidents, and timetable exceptions include `semesterId`. `periodId` is retained alongside any display-order number used by the current UI.

Browser-created teaching records remain append-only. Corrections and late submissions are new events. Browser code never performs a whole-database restore, semester activation, destructive cleanup, or Admin migration.

The generated Rules statically validate the confirmed active semester, class IDs, subject IDs, period IDs, and each class's exact valid-seat list. Rules also require the fixed single-teacher uid/role. Another teacher uses the same role shape only inside their own isolated Firebase project; this design is not multi-tenant.

## Fail-closed Firebase state

- No `.firebaserc` is bundled or generated by clone bootstrap.
- `.env.example` contains placeholders only.
- Real PINs and Secrets are never bundled.
- Before a teacher selects and authorizes a Firebase project, only demo/Emulator behavior is valid.
- `firebase.json` may define local deployment structure but does not confer a target or permission.

## Existing-site semester update

The 2026 reference production app is legacy v1: its documents and Rules do not contain `semesterId`. Do not claim that copying this template over it is a migration.

For a same-teacher update, first run the read-only planner and inspect the actual project/data. Choose one:

1. **Legacy read-only adapter**: preserve old documents byte-for-byte and map missing `semesterId` to the one known historical semester only for reads. All new writes use the new active semester ID.
2. **Controlled Admin migration**: after a separately authorized export/readback, add `semesterId` to existing documents, verify IDs/counts/hashes, then deploy semester-aware Rules and frontend.

The UI and Rules must both reject archived-semester writes. Rules are authoritative. Reopening an archived semester, rewriting append-only records, or deleting a third semester is never an ordinary browser action.

## Files never copied from a reference teacher

- `.firebaserc`, real `.env*`, `.secret.local`, service-account files;
- `.git`, `.firebase`, dependencies, build output, logs, sessions or cookies;
- source photos/workbooks, student names, exports, backups or production fixtures;
- production deployment records, teacher email, Firebase identifiers, source paths or source hashes;
- project-specific RDQ, handoff, QA history and attachment caches.

Use the allowlist and scanner in [security-and-sanitization.md](security-and-sanitization.md); never copy an entire teacher project tree into this asset.

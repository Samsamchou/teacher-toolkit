# 資料夾與交付

## 分類規則

四年級下學期、三年級上學期與三年級下學期的新資料都依正式單元及週次分類。先從正式課程確認名稱與週次，再建立：

`<正式單元名稱> 第<起始週>-<結束週>週`

不可先猜名稱或週次。學期上層只保留單元資料夾、`00_<學期>單元資料夾索引.md` 及必要說明；不得散落單元教案、教材或重建腳本。

尚未開始的正式單元資料夾放簡短 `README.md`，只標示正式名稱、週次、來源與「尚未開始」，讓 GitHub 保留分類；不要虛構進度或教學內容。

## 單元與節次結構

正式節數只能由該年級、該學期的正式「在地課程」來源確認，不可直接用週次跨度猜測。確認為 N 節後，單元根目錄必須恰有 N 個節次資料夾，依序命名：

`01_第1節/`、`02_第2節/`……`<NN>_第N節/`

單元根目錄只保留真正跨節共用的內容：

- `00_工作索引.md`：狀態、來源、成果、確認關卡與下一步。
- `01_<單元>_來源追溯與設計決定.md`。
- `02_<單元>_<節數>節骨架.md`。
- 無法合理歸屬單一節次且確實供多節共用的教材；大型共用資料只保留一份權威版本，由各節索引連結。
- 同時涵蓋多節的搬移清冊與回復證據可放單元根目錄 `_history/`；單一節次備份不得放在此處。

每個已開始的節次資料夾使用下列結構：

- `00_第N節工作索引.md`：列本節狀態、正式成果、支援資料、QA及下一步。
- `03_...` 起或既有檔名：本節正式詳案、教材草稿、教師用表、題庫、PDF及圖片資料夾；既有編號不因搬移而重排。
- `_work/`：本節重建腳本、結構化資料、中介檔與 staging。
- `_qa/`：本節渲染圖、檢查報告與測試證據。
- `_history/`：本節舊版備份、失敗候選及版本清冊。

尚未開始的節次資料夾放短 `README.md`，只列正式單元、節次、來源與「尚未開始」；動工後更新狀態，不留下錯誤的未開始標示。單元根目錄不得保留 `_work/`、`_qa/`、`_staging/`、`_backup/`，也不得散落任何名稱或內容可判定為單一節次專用的檔案或資料夾。

既有檔名可保留；若搬移，先建立清冊和 SHA-256，搬移後核對檔數、總位元組、雜湊、引用路徑及 Git diff。歷史 confirmed RDQ 與對話保留原文，不回寫歷史契約。

## 標準交付

1. 來源追溯 Markdown。
2. 可編輯 Word 詳案；不覆寫基線 Word。
3. 結構化課程資料，例如 Python、JSON 或 YAML，供重建與驗證。
4. 詳案列出的手作教材逐項附「詳案理解用／非正式教材」內容與操作草圖；每張草圖須能對回詳案中的名稱、尺寸、數量、操作步驟、圖像鷹架、學生填答處及教師答案。教師確認後才建立正式教材草稿、學生版／教師解答版教材檔、來源／提示詞紀錄與 QA 報告。
5. 若教師明確選擇網站，再加入網站原始碼、測試與安全文件。

Word 詳案至少包含單元／節次定位、原始來源、替換決定、學習目標與證據、課前教材、核心英語、四階段教學、評量及追溯。版面驗證須包含結構讀回與逐頁渲染檢查。

## 工作狀態

在索引中清楚標示：`尚未開始`、`草稿待教師確認`、`教師已確認`、`製作中`、`QA通過`。不要因檔案已建立就自動視為教師確認或完成。
